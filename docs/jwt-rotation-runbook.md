# JWT_SECRET rotation runbook (production, five services)

Status: PREPARED ONLY. Production has not been changed. Do not execute any step
below until the user has given an explicit go-ahead for the rotation window.

Scope: `auth`, `audit`, `master`, `risk`, `analytics` on the VPS (auditsphere.app).
Plan reference: `docs/backend-enhancement-plan.md` item A1.

Never paste a secret value into a terminal transcript, chat, ticket or commit.
Compare values only by a SHA-256 prefix (first 12 hex characters).

---

## 0. Facts this runbook depends on (verified in the repo, 2026-10-15)

- Production env file: `/root/auditsphere-deploy/.env`, mode `600`. `JWT_SECRET`
  lives here. `docker-compose.prod.yml` reads it through `${JWT_SECRET:?...}`
  substitution (5 services), so compose must be run with
  `--env-file /root/auditsphere-deploy/.env` or from a directory where that file is
  the project `.env`. Verify this in step 2.
- The repo `backend/docker-compose.prod.yml` still runs seeders on every start
  (`auth seed`, `audit seed`, `master seed`, line 106, 164, 187). The seeders
  overwrite production rows. The **no-seed override must always be passed**:
  `/root/auditsphere-deploy/docker-compose.prod.noseed.yml`. It is generated by
  `backend/deploy-prod.sh` (`write_override`). Never run `docker compose up`
  for these services without `-f` pointing at that override.
- `backend/deploy-prod.sh` `write_override` currently writes a **literal**
  `JWT_SECRET` under `analytics-service`. The override file on the VPS may still
  contain that literal. Step 3 removes it so analytics reads the env value.
  The repo fix (removing the literal from `deploy-prod.sh`) must land before the
  next deploy, or the next deploy regenerates the literal.
- `risk-service` must be running commit `4fde0c9` or later
  (`fix(risk-service): stop deleting audit universe rows on boot`, on `staging`)
  before any restart. Older risk code deletes audit-universe rows on boot.
  Verify in step 1.
- The override sets `SEED_ON_BOOT=false` for risk. Keep it.
- Old tokens and the old secret are treated as compromised (plan A1). Every
  session ends at the rotation. Users must log in again.

## 1. Preconditions (read-only checks)

1. Confirm risk code on the VPS includes `4fde0c9`:
   ```
   git -C /app/rbia-repo merge-base --is-ancestor 4fde0c9 HEAD && echo OK || echo TOO_OLD
   ```
   If `TOO_OLD`, stop. Deploy the current `staging` risk code first with
   `backend/deploy-prod.sh --ref <ref> risk`.
2. Confirm the no-seed override exists and is mode `600`:
   ```
   ls -l /root/auditsphere-deploy/docker-compose.prod.noseed.yml /root/auditsphere-deploy/.env
   ```
   Do not `cat` the `.env` file.
3. Confirm all five containers are healthy and running:
   ```
   docker ps --filter name=rb_audit_ --format '{{.Names}}\t{{.Status}}'
   ```
4. Take a fresh database backup. `backend/deploy-prod.sh` takes a verified
   `pg_dumpall` before a deploy. Rotation does not change data, but this is the
   recovery point if anything goes wrong.
5. Announce the window to users. Expected effect: every logged-in session ends.
6. Prepare a saved test token before the window (step 7). Use a dedicated test
   account with the `VIEWER` role. Store the token in a `600` file outside the
   repo and never print it.

## 2. Generate the new secret on the VPS (value never printed)

Run on the VPS. The new value goes straight into the env file.

```
umask 077
OLD_HASH=$(grep '^JWT_SECRET=' /root/auditsphere-deploy/.env | cut -d= -f2- | sha256sum | cut -c1-12)
cp -p /root/auditsphere-deploy/.env /root/auditsphere-deploy/.env.pre-rotation.bak   # rollback copy, see section 8
NEW=$(openssl rand -base64 64 | tr -d '\n')
# Replace only the JWT_SECRET line; keep every other key unchanged.
awk -v v="$NEW" 'BEGIN{done=0} /^JWT_SECRET=/{print "JWT_SECRET=" v; done=1; next} {print} END{if(!done) print "JWT_SECRET=" v}' \
  /root/auditsphere-deploy/.env > /root/auditsphere-deploy/.env.new
unset NEW
chmod 600 /root/auditsphere-deploy/.env.new
mv /root/auditsphere-deploy/.env.new /root/auditsphere-deploy/.env
NEW_HASH=$(grep '^JWT_SECRET=' /root/auditsphere-deploy/.env | cut -d= -f2- | sha256sum | cut -c1-12)
echo "old=$OLD_HASH new=$NEW_HASH"
```

Expected: `old` and `new` differ, and neither value appears on screen. If the two
prefixes are equal, stop: the secret did not change.

Also check that the new value is at least 64 bytes of base64 (about 88 chars).
Do this with a length count, not by printing it.

## 3. Remove the literal from the no-seed override

Edit `/root/auditsphere-deploy/docker-compose.prod.noseed.yml` (not the repo copy):

- Delete the `JWT_SECRET:` line under `analytics-service.environment`.
- Analytics then reads `${JWT_SECRET}` from the env file through the base compose
  file. If the base file has no entry for analytics, add
  `JWT_SECRET: ${JWT_SECRET}` under `analytics-service.environment` in the
  override instead. Do not write a value.

Keep a copy of the old override as `*.pre-rotation.bak` (mode `600`).

## 4. Validate the compose resolution without printing values

```
cd /root/auditsphere-deploy
docker compose --env-file .env \
  -f /app/rbia-repo/backend/docker-compose.prod.yml \
  -f docker-compose.prod.noseed.yml config --quiet && echo COMPOSE_OK
```

Do not run `docker compose config` without `--quiet` (it prints secrets).

## 5. Restart all five services together (no build, no recreate of the others)

```
cd /root/auditsphere-deploy
docker compose --env-file .env \
  -f /app/rbia-repo/backend/docker-compose.prod.yml \
  -f docker-compose.prod.noseed.yml \
  up -d --no-deps auth-service audit-service master-service risk-service analytics-service
```

Rules for this command:
- Always pass the no-seed override (`-f ...noseed.yml`).
- Always pass `--no-deps` and name the five services. Do not use a bare `up`,
  `--remove-orphans`, `--force-recreate` for the whole stack, `down`, or prune.
- Do not add `--build`. This step changes env only; code is deployed separately.
- Do not touch postgres, redis, kafka, zookeeper, kong, python-ai or the frontend.

Expected 401 window: from the first container recreate until the last one is
healthy. This is seconds to a few minutes. Within the window, a token signed with
the old secret gets 401 on any service that has already switched, and a token
minted by a service that has not switched yet gets 401 on the others.

## 6. Verify the running secret matches the file (hash only)

For each container, compare a SHA-256 prefix of the in-container value with the
file. Do not print either value.

```
for c in auth audit master risk analytics; do
  IN=$(docker exec rb_audit_${c}_service sh -c 'printf %s "$JWT_SECRET" | sha256sum' | cut -c1-12)
  echo "$c in-container=$IN file=$NEW_HASH"
done
```

Use the `NEW_HASH` from step 2 (re-derive it from the file if the shell was
reset). Every line must show the same prefix as the file. Any mismatch, or an
empty value, means that service has not picked up the env value. Stop and roll
back (section 8).

Then confirm no service is still on the literal from the override:
`grep -c 'JWT_SECRET:' /root/auditsphere-deploy/docker-compose.prod.noseed.yml`
must return `0`.

## 7. Saved token test and functional smoke

Run after the restart has settled (all five healthy).

1. Saved token test. Use the pre-rotation token from the `600` file. Send it to
   one read endpoint on each service. Expected: `401` on all five. A `200` means a
   service still accepts the old secret. Stop and investigate.
2. Fresh login. Log in with the test account through Kong
   (`POST /api/v1/auth/login`). Expected: `200` with a new token.
3. With the new token, call one list endpoint per service
   (auth users, audit charters, master companies, risk registers, analytics).
   Expected: `200`.
4. With no token, call the same endpoints. Expected: `401`.
5. Role deny check. Use the `VIEWER` test token on a mutating endpoint.
   Expected: `403` once plan A3 is live. Before A3 ships, a `200` here is
   expected and is not a rotation failure. Record it as a known gap.
6. Check logs for the old token value. Old logs still contain tokens from before
   A9 is live. Rotation invalidates them, but record that they exist.

---

## 8. Rollback

Use rollback only when all of the following hold: login is broken for everyone,
and the cause is the rotation itself, not an unrelated fault.

1. Restore the previous env file:
   `mv /root/auditsphere-deploy/.env.pre-rotation.bak /root/auditsphere-deploy/.env`
   (keep mode `600`).
2. Restore the previous override:
   `mv /root/auditsphere-deploy/docker-compose.prod.noseed.yml.pre-rotation.bak /root/auditsphere-deploy/docker-compose.prod.noseed.yml`.
3. Re-run step 5 with the same command. Re-run the step 6 hash check against the
   restored file.
4. Record the rollback. The old secret is compromised. Rolling back restores a
   known-exposed secret, so the decision and the time window must be written down.
   Plan a second rotation as soon as the cause is fixed.
5. Delete the `.pre-rotation.bak` files once rotation is accepted. Do not keep
   the old secret on disk longer than the rollback window.

---

## 9. Post-rotation

- Remove the `.pre-rotation.bak` files after sign-off (step 8.5).
- Confirm `backend/deploy-prod.sh` and the repo `docker-compose.prod.yml` no longer
  contain a secret literal (done in the repo change set; check before the next deploy).
- The next `deploy-prod.sh` run regenerates the override from its own
  `write_override`. Confirm that function no longer writes `JWT_SECRET` as a
  literal before running it.
- Record the rotation date in the change log. Do not record the value.

---

## 10. Repo change: compose and deploy files read JWT_SECRET from the environment

- `backend/docker-compose.yml`, `backend/docker-compose.dev.yml` and
  `backend/docker-compose.prod.yml` no longer contain a literal or fallback
  `JWT_SECRET`. Every service reads `${JWT_SECRET:?...}`. Compose fails with
  "JWT_SECRET missing" if it is unset.
- `backend/deploy-prod.sh` `write_override` now sets analytics `JWT_SECRET` to
  `${JWT_SECRET:?...}` instead of a literal. The no-seed behaviour is unchanged.
- Before the next deploy, the server must have `JWT_SECRET` set (same value as
  the auth-service stack) in `/root/auditsphere-deploy/.env` (mode `600`).
  Note: `deploy-prod.sh` runs compose from `/app/rbia-repo/backend` without
  `--env-file`, so that file is not read automatically there. Make the value
  reach that compose run another way: export it in the deploy shell, or keep it
  in the project `.env` at `/app/rbia-repo/backend/.env`. Confirm this on the VPS
  with a hash-only check (section 6) before deploying.
- Local development now also needs `JWT_SECRET` set (shell or `backend/.env`).
  Without it, `docker compose` fails by design.
